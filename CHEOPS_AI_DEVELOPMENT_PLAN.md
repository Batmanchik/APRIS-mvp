# Cheops AI: План Развития Продукта и Платформы

Дата: 21 марта 2026  
Статус: Draft v1 (рабочий план для реализации)

## 1) Контекст и Цель

Проект меняет позиционирование и название: **APRIS -> Cheops AI**.  
Цель плана: превратить текущий MVP в устойчивую, масштабируемую аналитическую платформу для раннего выявления пирамидальных рисков, с фокусом на:

- редизайн пользовательского опыта и интерфейса;
- усиление ML-составляющей;
- надежную инженерную и MLOps-базу для эксплуатационного режима.

## 2) Целевое Видение Cheops AI

Cheops AI — это Risk Intelligence Platform, где:

- аналитик получает стабильный поток алертов с прозрачным приоритизатором;
- руководитель видит качество модели, объемы обработки и риски по сегментам;
- инженерная команда может безопасно выпускать улучшения без деградации модели и UX.

## 3) Ключевые Направления Развития

## 3.1 Редизайн и UX

- Полный редизайн визуальной системы под бренд Cheops AI.
- Пересборка пользовательских сценариев: `Сканирование -> Очередь алертов -> Досье -> Решение`.
- Введение дизайн-системы: типографика, цветовые токены, компоненты, состояния, паттерны данных.
- Усиление explainability в интерфейсе: понятные причины риска, доверие к скору, контекстные подсказки.

## 3.2 ML и Данные

- Переход к формальной ML-постановке с бизнес-метриками.
- Усиление ETL для реальных источников данных (CSV/JSON + унифицированные схемы).
- Бенчмаркинг и выбор лучшего табличного алгоритма (LightGBM/CatBoost/XGBoost).
- Калибровка вероятностей, мониторинг дрифта, план переобучения.

## 3.3 Архитектура и Эксплуатация

- Закрепление API-first архитектуры (UI только через HTTP API).
- Batch scoring через отдельный endpoint и асинхронную обработку.
- Контейнеризация (Docker + docker-compose), предсказуемые окружения.
- Наблюдаемость: health, логи, метрики, контроль деградаций.

## 3.4 Качество и Процессы

- Полный тестовый контур: unit + api + smoke + контрактные тесты.
- Quality gate: pytest, ruff, mypy, pre-commit, CI.
- Регламент релизов и откатов (модель, API, UI).

## 4) KPI и Критерии Успеха

Минимальные целевые KPI на этап Cheops AI v1:

- ML:
- ROC-AUC >= 0.97 на контрольном датасете.
- Recall класса высокого риска >= 0.92 при контролируемом FP-rate.
- Калибровка вероятностей: Brier score улучшается относительно текущего baseline.

- UX/Product:
- Время до ключевого действия аналитика (от открытия до решения по алерту) сокращено на 30%.
- Не менее 80% тестовых сценариев выполняются без ошибок UX.
- Доля успешных batch-обработок >= 99%.

- Reliability:
- Uptime локального стенда >= 99% в рабочих окнах.
- P95 ответа API `/predict` <= 300ms (без batch).
- Все релизы проходят CI quality gate.

## 12) Стратегия Масштабной Автоматизации: ИП/ТОО + Скрытые Метрики (Новый приоритетный трек)

### 12.1 Почему это приоритет

Цель Cheops AI на следующем уровне зрелости: не только точечно скорить отдельные кейсы, а **поточно и автоматически обрабатывать большие очереди юридических субъектов (ИП/ТОО)** с минимальной ручной нагрузкой на аналитика.

Ожидаемый эффект:

- кратный рост пропускной способности анализа;
- более стабильный и воспроизводимый риск-скрининг;
- лучшее обнаружение сложных схем (легальные + крипто-маршруты);
- меньше зависимости от субъективных ручных оценок.

### 12.2 Целевой результат трека

К концу трека система должна обеспечивать:

- Batch-анализ крупных пакетов кейсов по ИП/ТОО с контролем SLA;
- Автоматическое ранжирование очереди алертов по приоритету расследования;
- Расчет расширенного набора скрытых (латентных) метрик риска;
- Explain-профиль по каждому кейсу в терминах типологий и причин;
- Контур обратной связи (разметка аналитика -> дообучение/калибровка).

### 12.3 Архитектура потока (Target Flow)

`Ingestion -> Entity Resolution (ИП/ТОО) -> Feature Factory -> Hidden Metrics -> Score v2 -> Alert Prioritization -> Dossier -> Analyst Feedback -> Retraining`

Ключевые инженерные блоки:

1. `Ingestion Gateway`
- Источники: CSV/JSON, выгрузки банка, внутренние транзакционные срезы.
- Контракты: versioned schema, обязательные поля, контроль качества входа.

2. `Entity Resolution Layer`
- Нормализация идентификаторов ИП/ТОО.
- Дедупликация и связывание нескольких идентификаторов одного субъекта.
- Построение устойчивого `entity_key` для агрегаций и истории.

3. `Feature/Signal Factory`
- Базовые операционные признаки.
- Временные признаки (окна 24ч/7д/30д/90д).
- Сетевые признаки по маршрутам средств.

4. `Hidden Metrics Engine`
- Вычисление латентных/подпольных индикаторов по графу и времени.
- Версионирование формул метрик и обратная совместимость.

5. `Scoring + Prioritization`
- `global_risk + typology_probs + urgency_score`.
- Приоритизация очереди с учетом риска, новизны и операционного контекста.

6. `Feedback Loop`
- Разметка аналитика: confirmed / rejected / pending.
- Использование обратной связи для калибровки порогов и последующего retraining.

### 12.4 Библиотека скрытых метрик (v1)

Минимальный обязательный набор:

1. `Layering Velocity Index (LVI)`
- Скорость прохождения средств через цепочки контрагентов за малые окна времени.
- Сигнал для ускоренного дробления и перенаправления потоков.

2. `Bridge Asymmetry Score (BAS)`
- Асимметрия между legal-входом и crypto-выходом (или наоборот).
- Сигнал мостов между формально легальными и крипто-каналами.

3. `Counterparty Dispersion Shift (CDS)`
- Резкая смена распределения контрагентов относительно исторического профиля.
- Сигнал резкой тактической перестройки схемы.

4. `Circular Flow Probability (CFP)`
- Вероятность циклического возврата средств через связанные узлы.
- Сигнал имитации оборота/искусственного движения средств.

5. `Structuring Intensity Score (SIS)`
- Интенсивность дробления платежей около порогов/лимитов.
- Сигнал структурированного splitting для обхода контроля.

6. `Centrality Drift Delta (CDD)`
- Сдвиг центральности ключевых узлов сети во времени.
- Сигнал смены бенефициаров/центров управления потоком.

7. `Behavioral Regime Change (BRC)`
- Детектор смены поведенческого режима ИП/ТОО.
- Сигнал «до/после» для раннего обнаружения новых схем.

Для каждой метрики фиксировать:
- формулу/алгоритм;
- диапазон и expected behavior;
- устойчивость к шуму;
- вклад в модель и explainability.

### 12.6 KPI трека

Функциональные:
- Доля автоматизированно обработанных кейсов ИП/ТОО >= 90% в целевом потоке.
- Доля кейсов с полноценным explain-профилем >= 95%.

ML/риск:
- Recall high-risk сегмента растет относительно текущего baseline.
- Calibration (Brier/ECE) не ухудшается при добавлении hidden metrics.

Операционные:
- Batch success-rate >= 99% на целевом размере.
- P95 batch endpoint в пределах согласованного SLA.
- Снижение времени аналитика на первичную сортировку алертов.

### 12.7 Риски и контроль

Риск 1: Слишком много новых метрик -> нестабильность модели.
- Контроль: staged rollout, ablation-тесты, включение метрик поэтапно.

Риск 2: Ошибки entity resolution -> неверные досье.
- Контроль: deterministic rules + conflict checks + ручной sampling-аудит.

Риск 3: Рост latency при больших батчах.
- Контроль: профилирование hot-path, ограничение batch-size, degrade-mode.

Риск 4: Переусложнение explainability.
- Контроль: фиксированный формат explain, top-K факторов и confidence.
