## Правила, по которым принимается работа

1. **Ветка на задачу.** Одна задача — один коммит в свою ветку, не в `main`.
   Не смешивать две задачи в одном диффе.
2. **Никакой правки существующей математики без задачи из этого файла.**
   Формула, которая меняет вес каждого ребра в графе, — это архитектурное
   решение, а не оптимизация.
3. **Перед сдачей запускать `python scripts/check_all.py`.** Все шесть гейтов.
   Если гейт красный — задача не сдана.
4. **Новая функция без теста не принимается.** Тест должен *кусаться*: сначала
   покажи, что он падает на дефекте, потом что проходит на фиксе.
5. **Заявленное число должно быть воспроизводимо командой.** «Отработало за
   1.14 с» без скрипта в репозитории — это не измерение.
6. **Ветка от свежего `main`, одна на задачу, номер задачи в названии.**
   `git fetch origin && git checkout -b agy/3.8-crypto-channel origin/main`.
   Работу субагентов сводить в неё **разбирая, что изменил каждый**: при
   слепом мерже двух субагентов, правивших один файл, побеждает последний, и
   потерю никто не замечает.
7. **Новая зависимость объявляется в `pyproject.toml`.** Тест, которому нужен
   необязательный инструмент (профилировщик, драйвер), обязан
   **пропускаться** через `pytest.importorskip`, а не ронять весь прогон.
   Один отсутствующий пакет не должен красить гейт, который к нему не
   относится.
8. **Перед сдачей — прогон на чистом окружении.** Пустое виртуальное
   окружение, `pip install -e .[dev]`, `python scripts/check_all.py`. Ровно
   на этом шаге ловятся необъявленные зависимости, и без него правило 3 не
   работает: на вашей машине пакет стоит с прошлой задачи.
9. **Одноразовые скрипты не коммитятся.** Абсолютный путь с вашей машины
   внутри файла — признак, что файлу не место в репозитории. Результат
   работы — изменённый исходник, а не инструмент, которым вы его меняли.

**Изменение генератора, признаков или разбиения — первая строка отчёта,**
отдельно от списка задач. Оно обесценивает все ранее измеренные числа, и
человек, который об этом не знает, продолжит их цитировать.

Ветку `analyze_project_architect_role` **не продолжать**: она тащит старую
историю, и отделять в ней новое от забракованного приходится вручную. Новые
задачи — только от свежего `main`, по правилу 6.

### Почему порядок был именно такой: сначала данные, потом метрика

**Это уже сработало:** 3.8 сдана, и `BAS` (3.9) из «нечего читать» стала
обычной задачей. Ниже — исходное рассуждение, оно остаётся в силе для `SIS`
(3.10 → 3.11).

`LVI`, `BAS` и `SIS` — правильные метрики в неправильном порядке. Претензия не
к формулам, а к тому, что **данных, которые они читают, в мире не существует**:

| метрика | читает | есть в генераторе? |
|---|---|---|
| `LVI` скорость прохождения по цепочкам | слоирование | нет — задача 3.8 |
| `BAS` асимметрия легальный вход / крипто-выход | крипто-канал | нет — ни одного события `channel="crypto"` |
| `SIS` интенсивность дробления у порогов | дробление сумм | нет — задача 3.10 |

Написать `SIS` сейчас можно. Проверить — нет: тест сядет на рукодельных
фикстурах, пройдёт, и будет **воздерживаться** на реальном мире, потому что ни
одно событие в нём не является дроблением. Это способ, которым гейт
проваливается вхолостую: проверка корректна, а данные не доходят до ветки, где
она бы возразила. `lint-imports` показывал `KEPT` на Elasticsearch в `domain`
ровно по этой причине.

Поэтому: `3.8` даёт события → `BAS` становится измеримым (`3.9`); `LVI` уже
наполовину есть — это `W` из `3.1`, `Σ v_k·e^(−λΔt_k) / Σ_in`, не пишите вторую
формулу для того же, допишите ту; `SIS` — вместе с дроблением (`3.10`, `3.11`).

## 3.1 `W` как взвешенная по объёму доля с индивидуальным затуханием

Новый модуль `src/apris/cheops/infrastructure/ml/flow_weight.py`.

```python
def flow_weight(account, events, *, lam_per_hour) -> float | None
```

* Считать через `fifo_match` из `legacy_features_v2` — не писать сопоставление
  заново.
* `W = Σ v_k·exp(−lam·Δt_k[час]) / Σ_in`, где `Σ_in` — весь приход в окне.
* `Σ_in == 0` → вернуть `None`. Не 0.0. Отсутствие ответа и ответ «ноль» —
  разные вещи, и вызывающая сторона обязана их различать.
* `lam_per_hour` — обязательный аргумент без значения по умолчанию. Дефолт
  здесь означал бы, что одна `λ` годится и минутам, и месяцам.
* Экспортировать две именованные константы с обоснованием в комментарии:
  `LAMBDA_FAST` (мульская вспышка) и `LAMBDA_SLOW` (пирамида).

Тесты (минимум, каждый — отдельная функция):
1. чистый транзит: пришло 100, ушло 100 через 10 минут → `W` близко к 1.0;
2. тот же транзит через 30 суток при `LAMBDA_FAST` → `W` близко к 0.0;
3. счёт только тратит, прихода нет → `None`;
4. `0.0 <= W <= 1.0` на 200 случайных счетах из сгенерированного мира;
5. **перестановка событий в списке не меняет `W`** — прямая проверка;
6. магазин (оборот вошёл и вышел, но с задержкой в дни) и мул (минуты)
   различаются при `LAMBDA_FAST` — это и есть смысл признака.

Никуда не подключать. Задача заканчивается на модуле и тестах.

## 3.8 Крипто-канал в генераторе

**Это первый пункт критического пути, важнее 3.1–3.6.** Три типологии из пяти
(`LEGAL_LAYERING`, `LEGAL_TO_CRYPTO_BRIDGE`, `CRYPTO_MIXING`) объявлены в
`domain/typologies.py`, считаются в `domain/contracts.py` и **никогда не могут
сработать**: генератор не выпускает ни одного события с `channel="crypto"`.

Нужно в `infrastructure/simulation/generator.py`:

1. новая популяция `_gen_crypto_layering(b, ...)` — легальный вход, 2–4 слоя
   переводов между подставными счетами, затем мост в крипту
   (`channel="crypto"`, `asset_type="crypto"`), затем дробление между
   несколькими крипто-адресами;
2. честный аналог `_gen_crypto_traders` — люди, которые просто покупают
   крипту. **Без него любой детектор выучит «крипта = мошенничество»**, и
   это будет не результат, а тавтология;
3. в `SimulationConfig` два счётчика с дефолтами и комментарием об источнике;
4. `ALLOWED_CHANNELS` уже содержит `"crypto"` — проверить, что контракт
   пропускает, и что `contracts.py` начинает возвращать ненулевые значения по
   этим трём типологиям.

Приёмка: тест, который прогоняет мир и утверждает, что каждая из трёх
типологий срабатывает хотя бы на одном кейсе **и не срабатывает на честных
крипто-трейдерах**. Плюс число в отчёт: сколько кейсов каждой типологии.

## 3.13 Скорость генератора

Один мир (120 дней, 25 тысяч счетов) строится ~66 секунд, полный набор
картинок — 200. Лестница потребует полусотни прогонов. Профилируйте
(`cProfile`), найдите три самых дорогих места, ускорьте. **Единственное
условие приёмки, которое важнее скорости:** при том же сиде мир должен
получаться **побайтно тот же**. Тест: собрать мир до и после, сравнить хеш
последовательности событий. Ускорение, меняющее данные, — это не ускорение,
это другой эксперимент.

  Результаты в `docs/RESULTS.md`: там сказано, что уже измерено, чтобы вы не
  мерили это второй раз.

GNN, SHAP и Federated Learning **пока не берём**. Сначала должна стоять честная
базовая линия, иначе не с чем сравнивать: GNN, который обыгрывает сломанный
бейзлайн, не измеряет ничего.

## Как отчитываться

Отчёт по задаче — в `MULTI_AGENT_SYNC.md`, раздел «Обратно в этот файл».
По каждой задаче: номер, ветка, вывод `check_all.py`, и **числа, а не оценки**.
«Быстро» и «протестировано» — не результат. `0.7206`, `4.2 %`, `+0.071` —
результат.
